# EchoMoments MVP implementation audit

Last reviewed: 2026-10-28. This audit describes the current working tree; deployment credentials and provider state are not part of this repository.

## Agreed MVP behavior

| Area | Current state | Remaining verification or work |
|---|---|---|
| Account-based event access | Hosts create events; signed-in members join public events using the host's event code/link. A member must join before viewing the album. No viewer/member-count cap is applied, and host member controls are paginated at 50 per page. | Private/hidden invitation and password flows are not implemented. |
| Upload capacity | Host can configure event total, host allocation, shared guest pool, optional default member cap, and individual member overrides. Upload permission can be disabled per member. Queued jobs reserve capacity; caps cannot be reduced below existing saved/queued usage through the host UI. | Exercise cap edits and simultaneous uploads against a hosted Postgres database. |
| Upload queue | Each file becomes its own database-backed job with a private staged object, idempotency key, status, retry count, and host-first scheduling. Browser submission is bounded to three concurrent files and polls each job as soon as it is accepted. A bounded guest turn prevents an aged guest queue from continuously outranking host work; conditional claims retry collisions across PostgreSQL workers. Transient browser/network and worker save failures retry automatically; terminal failures can be requeued without selecting the file again. `runserver` does not start workers; `serve_demo` does. | Run multi-user queue scenarios against the actual object store and hosted database. |
| Shared album | Saved event photos are membership-gated and paginated at 20 by default, with 30/50 page-size choices for hosts and members; the personal album uses the same choices. The album remains available after the host ends uploads. View/download endpoints check membership and downloads respect the host setting. | Confirm behavior after deployment and decide whether local event data/photos should be imported. |
| Personal photo album | Optional selfie enrollment supports file upload, mobile camera picker, and explicit live-camera capture. Camera permission is requested only after the member enables the camera. Enrollment requires consent and exactly one detected face. YuNet/SFace suggestions are private to the member; wrong matches can be hidden; one, selected, or all visible matches can be downloaded; revocation deletes the encrypted template and suggestions. The selfie is not retained. | Check recognition quality on representative event photos and monitor scan cost/latency. |
| Privacy and storage | Event images, covers, profile photos, and staged uploads use private local storage in development or S3-compatible private storage when `USE_S3=True`. Django serves files after authorization. Face embeddings are encrypted. Uploads enforce a JPEG/PNG/GIF/WebP allowlist plus 10 MB/30 MP limits, inspect actual bytes, fully decode frames, and reject malformed images and trailing payloads. Browser filters and Django Admin forms use the same allowlist; stored/response MIME types and extensions derive from verified bytes. File cleanup runs after commit on record deletion/replacement. Production settings require private S3 storage and a valid dedicated face key. | Cloudflare R2 is recommended for photos and Neon for Postgres; neither has been provisioned. Verify the private bucket and credentials before deployment. |
| Admin | Django admin exposes event/member controls, capacity and upload status, and read-only queue/photo/face-scan inspection. Raw encrypted face embeddings and direct private file URLs are not exposed. Event cover and profile uploads use the shared image validator. | Confirm staff/superuser accounts and permissions after deployment. |
| Free demo setup | `render.yaml` configures one Render web process with Waitress and queue threads; Postgres and private S3-compatible storage are external. Python is pinned to 3.12.10. Django connection health checks are enabled. | Configure the recommended Neon/R2 resources, deploy when requested, and exercise the live app. Render Free sleeps after 15 minutes idle, so the first request can take about a minute. |

## Verification completed locally

- Installed the declared deployment dependencies in an ignored local `.venv` and ran Django 5.2.18.
- `manage.py check`: passed. `makemigrations --check --dry-run`: no changes detected. `migrate --check`: passed.
- `collectstatic` ran successfully after the responsive styles were added. Django's normal `check` found no template/system issues.
- OpenCV 4.14 loaded the downloaded, SHA-256-verified YuNet/SFace models through `manage.py check_face_matching`. A local 70-photo album was checked with one clear portrait as the reference. At the prior 0.363 threshold, 25 suggestions included 14 visually wrong low-score people; raising the default to 0.5 retained 11 visually consistent photos (including the reference). The real enrollment endpoint and index worker also returned 11 suggestions during a temporary probe. Consent, encrypted template, and test matches were cleared afterward. This is a single-album check, not a broad recognition benchmark.
- `pip check` reported no broken requirements. Python syntax compilation and `git diff --check` passed.
- `manage.py check --deploy` reported only Django's optional `security.W021` warning because HSTS preload is intentionally disabled.
- The Django suite passed all 30 tests in an isolated SQLite test database. Coverage includes event access, upload-cap reservations, allowed/invalid image types, size and integrity, safe MIME/ZIP names, queue processing/retries, host-priority scheduling, member pagination, post-event album access, opt-in face-index/revocation, selfie camera-choice rendering, and a synthetic one-face enrollment → encrypted-template → real face-index match flow. Admin access and admin image rejection are covered too. Python 3.14.7 is used locally; Render is configured for Python 3.12.10.
- Chrome was checked earlier in a 400 px responsive device viewport on the guest event page, My Photos, and the account dashboard. The My Photos GET was re-opened after the stale unavailable response; the selfie form and both source choices appear, and a hard reload confirmed the hidden empty preview no longer shows. Live camera permission was not requested. The signed-in local account has no hosted events, so the host-specific dashboard was not visually checked in Chrome.
- The local database initially had three queued uploads. The cause was running `runserver` without its separate worker processes. Both local workers were started; all three uploads and their face-index jobs completed. The temporary real-photo probe left no active enrollment or match rows; all 70 face-index jobs are complete.

## Known gaps before a public demo

- Cloudflare R2 for photos and Neon for Postgres are the recommended providers; no service, bucket, or credentials have been created/configured. No live deployment or upload to a real bucket has been verified.
- Local SQLite data and `private_media/` files do not automatically transfer to the hosted services.
- Private-event invites, password-gated join links, and no-account upload-only token links are not implemented. The current MVP uses signed-in accounts and event codes.
- Comments, tags, email notifications, payments, and extended role delegation are outside the current MVP implementation.
- Host-specific UI and the full upload/retry/download flow still need browser validation with a temporary host event. The live camera needs an on-device permission check, and recognition quality still needs broader validation across people, lighting, poses, and events. The local real-photo check is limited to one event/member; the synthetic test confirms the complete pipeline on an identical synthetic face.
- Uploads are still sent through the Django app, so the change reduces batch wait and avoids an app-server download/re-upload when staged and final objects share an S3 bucket. Cloudinary-like direct-to-storage upload has not been implemented; that would need signed upload endpoints and bucket CORS configuration.
